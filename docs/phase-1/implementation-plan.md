# 一期软件实施方案

## 1. 项目策略

一期采用“风险优先的纵向切片”，不是按分析层、后端层、前端层横向铺开。每个里程碑都必须产生可检查结果，失败时允许停止，不把失败包装成继续建设底座的理由。

角色责任由同一开发代理执行也必须分开验收：

| 角色 | 责任 |
| --- | --- |
| 产品经理 | 维护 `P1-*` 需求、用户问题和 GO/REVISE/STOP 门槛 |
| 项目经理 | 维护 OpenSpec `T*` 任务、依赖、状态和退出条件 |
| 软件设计 | 维护数据契约、模块边界、替换点和错误处理 |
| 开发 | 严格按 TDD 实现当前任务，不顺手建设后续能力 |
| 测试 | 执行自动检查、浏览器交互和目标用户理解测试 |

## 2. 里程碑

### M0 正式立项与基线

目标：建立公开仓库、唯一文档入口、OpenSpec 任务和可复现基线。

任务：

- `T0.1` 初始化 Git、开源许可证、README、忽略规则；
- `T0.2` 创建 GitHub public repository 并推送；
- `T0.3` 完成一期文档与 OpenSpec 校验；
- `T0.4` 验证旧原型仍可构建，记录它只是对照组。

退出条件：干净克隆不包含样例仓库、数据库、缓存、`node_modules` 或构建产物；文档链接有效；OpenSpec 严格校验通过。

### M1 模型契约与确定性校验

目标：先证明“什么样的语义图才算真实且完整”，避免先画出好看的错误页面。

任务：

- `T1.1` 写模型校验器的失败测试：缺少 band、重复 ID、悬空边、无证据对象、无效行号；
- `T1.2` 实现最小 JSON 校验器；
- `T1.3` 增加注册/登录真值门禁：成功、失败、事件和数据标签；
- `T1.4` 固定样例 manifest 与证据 schema。

退出条件：损坏 fixture 全部按预期失败，最小有效 fixture 通过；校验只使用 Node 标准库。

### M2 真实证据包

目标：从固定提交的真实 TypeScript 样例和 CodeGraph SQLite 生成有界、可核对的证据包。

任务：

- `T2.1` 提供样例获取和 CodeGraph 建图命令，不提交第三方源码；
- `T2.2` 查询固定 CodeGraph schema 的相关实体、关系和调用位置；
- `T2.3` 读取精确源码片段并限制路径/行号；
- `T2.4` 输出 `evidence.json` 和统计摘要；
- `T2.5` 人工抽查入口、分支、依赖注入、返回与事件事实。

退出条件：所有证据能回到固定提交；不存在越界路径；提取失败不发布半成品。

### M3 一次受约束的语义建图

目标：验证 AI 是否能从事实包生成功能层级和三层流程，而无需程序员重画。

任务：

- `T3.1` 编写只读证据、schema 约束和禁止编造的 authoring prompt；
- `T3.2` 由当前 AI 代理生成 `model.json`；
- `T3.3` 运行 M1 校验，逐条记录拒绝原因；
- `T3.4` 只允许纠正语义文案，记录任何人工拓扑修改；
- `T3.5` 发布验证通过的浏览器模型。

退出条件：零无证据主张、零关键路径遗漏、零错误条件/传递、零程序员手工拓扑重建。否则 STOP 或修改 prompt/schema 后重做。

### M4 最小理解界面

目标：验证用户能否用功能树、语义缩放和证据抽屉理解代码。

任务：

- `T4.1` TDD 实现纯函数语义相机；
- `T4.2` 用原生 SVG 一次渲染一个 band；
- `T4.3` 实现滚轮锚点缩放、中键 Pointer Capture 平移和可见祖先选择；
- `T4.4` 实现近指针悬浮、点击固定和碰撞处理；
- `T4.5` 实现源码抽屉，保持相机与选择状态；
- `T4.6` 建立功能树/流程两个独立 URL 和 BroadcastChannel 选择同步。

退出条件：`P1-1..P1-9` 的自动和手动交互检查通过；页面没有空白、重叠或惰性控件。

### M5 产品可行性评审

目标：由目标用户而不是开发者判断产品假设。

任务：

- `T5.1` 执行自动测试、构建和浏览器测试；
- `T5.2` 按手动测试方案完成真实性审查；
- `T5.3` 让目标用户完成理解题，全程不先读源码；
- `T5.4` 与旧点击下钻原型比较；
- `T5.5` 记录 GO/REVISE/STOP 和下一阶段授权范围。

退出条件：只依据 `docs/phase-1/README.md` 的成功标准判定。

## 3. 依赖与关键路径

```text
M0 -> M1 -> M2 -> M3 -> M4 -> M5
```

M4 的相机纯函数可以在 M2/M3 期间先做，但真实页面不得以假数据宣称验证完成。M2 失败时停止 M3-M5；M3 失败时不建设更多 UI。

## 4. 开发纪律

- 新行为先写失败测试，确认失败原因后写最少实现；
- 每个任务完成后更新 `openspec/.../tasks.md` 对应复选框；
- 每个里程碑独立提交，提交信息包含 `M*` 或 `T*`；
- 不修改 canonical design 来迁就实现；发现冲突先更新设计并重新走 Ponytail gate；
- 不把旧原型代码复制成新架构；只复用依赖和已验证的视觉方向；
- 生成文件必须标记来源并可重建；第三方样例和 CodeGraph DB 不入库。

## 5. 资源与进度估算

按单个熟练工程代理、用户可及时参与手测估算：

| 里程碑 | 预计工作量 | 主要不确定性 |
| --- | --- | --- |
| M0 | 0.5 天 | GitHub 命名与公开内容清理 |
| M1 | 1 天 | 模型真值门禁是否足够明确 |
| M2 | 1-2 天 | CodeGraph 固定 schema 与范围查询 |
| M3 | 1-2 天 | AI 建图准确率和需要的 prompt 轮数 |
| M4 | 2-3 天 | 三层稳定布局与交互可理解性 |
| M5 | 0.5-1 天 | 目标用户时间与反馈质量 |

总计约 6-9 个工作日。M3 是主要产品风险，不能用 M4 的界面完成度掩盖。

## 6. 一期完成定义

只有以下证据同时存在才可关闭一期：OpenSpec 任务完成、测试命令新鲜通过、真实模型校验通过、浏览器截图/交互记录、手测记录和明确决策。代码合并或页面可打开不等于一期完成。
